## 原始审阅输出

### A. 项目 / 产品层意见

#### 1. 项目方向成立,但 MVP 复杂度已经接近"小产品首版",不是轻 MVP

Zlzl 的核心判断是有吸引力的:用户并不缺一次性 AI 问答,缺的是能随学习过程
沉淀、复用、提醒和诊断的陪伴结构。"库 + 脉络 + 节点 + 信号"这套表达能把
产品从"又一个 AI 工具"里拉出来。

但当前上课模式 MVP 同时包含:

- 长录音。
- 课件 / 图片上传。
- ASR。
- LLM 总结。
- 知识点归一化。
- 脉络重写。
- 测验生成与评分。
- 掌握信号回写。
- 多次课后的留存验证。

这些每一项都可能单独拖慢进度。最大风险不是技术做不出来,而是做到很久以后
才发现用户其实没有被"脉络和记忆"打动。建议在 tasks 里标出一条
**最薄体验闭环**:哪怕先用 mock 转写 / 手动输入 / 人工触发云函数,也要尽早
看到"课后总结 → 脉络长大 → 做 3 题 → 状态变化 → 下次还能被记住"是否有感觉。

#### 2. 差异化必须落在"记忆证据",不是"课堂总结质量"

课堂总结是获客钩子,但不是护城河。总结质量再好,用户也会自然拿它和讯飞、
元宝、豆包、通用大模型比较。真正不一样的是:

- 它把本节课接到过去的课。
- 它知道哪些疑问还悬着。
- 它能把测验结果变成下一次学习路径的变化。
- 它让用户看到"这门课正在被我和 AI 一起推进"。

所以执行优先级上,不能只把 summary page 做漂亮。`library-detail` 里的
本次更新 delta、学伴便签、未解决问题、跨课关联,应该被视为核心验收项。
如果这部分弱,产品会退化成"自动笔记 + 出题"。

#### 3. 当前验证指标仍偏工程验收,缺少产品成败标准

`requirements.md` 的验收标准主要是功能是否可用,这对开发必要,但不足以判断
项目是否值得继续。建议另补一组 MVP 产品指标,例如:

- 首课后:用户是否愿意保存 / 分享 / 回看总结。
- 首课后 24 小时内:是否打开脉络或做测验。
- 第二次课后:是否能感知到跨课记忆和 delta。
- 连续两次课后:是否主动回到库主页,而不是只看总结节点。
- 测验完成率:用户是否真的愿意答 3 题。
- 纠错率:AI 总结错误是否高到破坏信任。

这些指标不一定一开始自动埋点,但至少要写进项目文档,否则容易用"功能跑通"
替代"假设被验证"。

#### 4. 目标用户还需要更窄

文档写"大学生课堂",但不同课堂差异很大:

- 文科 / 设计史这类叙述型课程适合总结、脉络和核心问题。
- 数学、编程、物理这类强练习课程,只靠课堂总结和开放题评分可能不够。
- 大课录音环境差,转写质量更不稳定。
- 需要课件 / 板书 / 图片时,多模态处理复杂度会迅速上升。

建议 MVP 明确首批试用课型,例如"概念密集、叙述型、考试以理解和论述为主
的大学课程"。这会直接影响 prompt、UI 文案、测验题型和成功标准。

#### 5. 合规不应只留到上线前

`concept.md` 把合规细节留到上线前处理,可以理解为当前不做完整协议,
但录音是产品第一步,会强烈影响用户信任。即使 MVP 是个人学习用途,
也建议在原型 / requirements 中提前放入轻量原则:

- 首次录音前明确提示仅用于个人学习。
- 提醒用户遵守课堂和他人授权要求。
- 明确录音、转写、课件会上传云端处理。
- 提供删除库 / 删除录音的入口规划。

这不是法务洁癖,而是产品信任的一部分。AI 学伴如果第一步让用户觉得
"我是不是在偷偷录别人",后面的陪伴感会被削弱。

#### 6. 冷启动不只是 demo 问题,也是产品叙事问题

DeepSeek 提到 demo 库或引导式首课是对的。但更根本的是:用户第一次打开时,
需要立刻理解"脉络会长大"。如果空库只显示"开始上课",用户会把它理解成录音器。

建议冷启动呈现:

- 一个示例库,展示 3 次课后的路径变化。
- 或者新建库后显示"第一次课后这里会长出什么"的轻量预览。
- 首课结束后,优先强调"我把今天和未来要追的问题接起来了",而不只是
  "总结生成完成"。

#### 7. 项目推进建议:先修文档,再进入阶段 0

当前文档已经足以证明方向,但还不适合直接开云开发基建。建议先用一个小修订
模块处理:

- 修 `prototype.md` 与 `prototype.html` 口径不一致。
- 修 `requirements.md` 已过期待确认项。
- 补"最薄体验闭环"和产品验证指标。
- 补冷启动方案。
- 补合规 / 删除数据的 MVP 级原则。

这一步完成后,再做阶段 0 会稳很多。

### B. 技术 / 执行层意见

### 1. High — 原型结构源与已定技术口径冲突

`docs/product/prototype.md` 自称是"结构事实来源",但录音页仍写"实时转写",
测验也写"支持语音作答"。这和 `design.md` 已定的"课后转写、不在课中推送
转写流"冲突,也和"语音作答是否纳入首版待确认"冲突。

建议先修 `prototype.md`,让它和 `prototype.html` 一致,否则后续 Agent 很容易
做错方向。

### 2. High — 长录音验收标准仍可能不可验证

`requirements.md` 要求"录音整节课 >=45 分钟;切后台 / 锁屏后已录数据不丢",
但 `design.md` 明确"小程序录音切后台 / 锁屏会中断"。这里需要把验收口径
改成:

- 前台连续录制 + 分段保存。
- 后台 / 锁屏 / 来电等中断时,已保存分段不丢。
- 中断后明确提示续录或课后补录。

不要暗含小程序可以后台继续录音。

### 3. Medium — requirements 的"待确认问题"已经过期

`requirements.md` 仍说 ASR、后端、存储、登录等技术决策"阻塞 design.md"。
但 `design.md` 已决定:

- 后端:微信云开发。
- 存储:云数据库 + 云存储。
- 登录:云开发 openid。
- 密钥:仅存在云函数环境变量。

建议拆成"已决策"和"仍待确认",只保留具体 ASR 服务商、LLM 模型、语音作答
是否进首版等真正未定项。

### 4. Medium — 冷启动补救没有进入执行包

`concept.md` 明确 DeepSeek 审阅后要求"冷启动首次价值:预置 demo 库或引导式
首课"写入执行包。但 `requirements.md` / `design.md` / `tasks.md` 里没有
对应验收或任务。

这个会影响 MVP 验证,因为零历史用户第一次打开产品时可能没有可感知价值。

### 5. Medium — 掌握信号与状态规则还不够落地

`concept.md` 规定信号格式应含:

```text
{知识点 ID, 信号类型, 值, 时间, 来源模块}
```

`design.md` 的 `MasterySignal` 只有 `type` / `timestamp` / `sourceModule`,
缺少 `value`、来源节点 / 模块实例、评分细节等。同时 `design.md` 引用了
"掌握状态规则"章节,但实际没有独立规则章节。

建议在实现前补一个小节:

- 信号字段。
- 状态转移规则。
- 多个知识点如何汇总成 station 状态。
- 测验、标记疑问、未测状态之间的优先级。

### 6. Medium — 异步流水线缺少幂等 / 重试契约

`design.md` 说 `advanceClass` 可由前端轮询或定时触发推进,但 `ClassSession`
只有 `status` / `nodeId` / `error`。如果前端重试、网络超时或云函数重复执行,
可能重复调 ASR / LLM,或重复写节点、知识点、信号。

建议在阶段 0 / 阶段 3 前补充:

- 每步 `jobId` 或外部任务 ID。
- `attempts`。
- `lockedUntil` 或等价执行锁。
- `updatedAt`。
- 幂等 key。
- 失败可重试策略。

## 结论

总体方向稳:产品概念、信息架构、执行包已经把"上课模式 MVP"收束得比较清楚,
DeepSeek 的关键意见也大多被吸收了。现在最该先修的是文档漂移和实现前契约:

- `prototype.md`
- `requirements.md`
- `design.md` 中的信号 / 流水线细节

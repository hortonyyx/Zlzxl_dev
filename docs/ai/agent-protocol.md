# 跨 Agent 协作协议

本项目用于 Codex、Claude Code、GPT-5.5、Opus 以及备用/跑腿模型之间的高强度 AI 协作。

## 协作模型

- 人负责产品方向和最终验收。
- GPT-5.5 和 Opus 主要负责规划、难点判断和高级审阅。
- Codex 和 Claude Code 主要负责编码实现。
- 跑腿模型可以总结、搜索、收集日志，但不要单独决定架构。
- Agent 之间是协作者，不是绝对真理来源。

## 新窗口启动

启动新模型窗口时：

1. 加载 `docs/ai/START_HERE.md`。
2. 如有当前功能，加载 `docs/specs/<feature>/` 下的执行包。
3. 只加载当前模块相关的代码文件。
4. 要求模型先复述目标、约束和下一步，再开始编辑。

## 交接格式

从一个 Agent 交给另一个 Agent 时，使用：

```md
## 目标

要改什么？

## 当前状态

已经改了什么，发现了什么？

## 当前模块

正在执行 `tasks.md` 里的哪一项？

## 涉及文件

- path/to/file

## 约束

- 重要规则或风险。

## 验证

- 跑过什么？
- 还需要手动测什么？

## 审阅请求

下一个模型重点看什么？审阅请求包落到哪里？
```

## 收工和 git 管理

- 开发 Agent 收工前必须同步三类状态：
  - 执行包任务状态：`docs/specs/<feature>/tasks.md`。
  - 长期上下文：`docs/ai/session-notes.md`。
  - 下个窗口交接：`docs/ai/NEXT_WINDOW.md`。
- 能 commit 时按主题分组提交，不把不相关改动塞进一个 commit。
- 推荐提交颗粒：
  - `fix:` 修 bug 或可靠性问题。
  - `feat:` 新功能或新能力。
  - `docs:` 文档和管理规则。
  - `chore:` 项目配置、目录整理、非业务性维护。
- 审阅请求 / 审阅结果归档与实现修复分开提交。
- 如果暂不 commit，必须在回复中列明工作区状态和建议提交分组。
- 未经用户明确要求，不回退其他 Agent 或用户的未提交改动。

## 冲突规则

- 没读当前文件内容前，不要覆盖文件。
- 两种方案冲突时，默认保留更小且可工作的方案，除非用户另有选择。
- 架构变化必须记录到 `docs/ai/session-notes.md`。
- 大改动必须拆成模块。
- 审阅意见不自动等于结论，要结合项目目标和当前代码判断。

## 审阅检查

- 是否匹配当前执行模块？
- 页面是否保持轻量？
- API 调用是否集中？
- storage 和 toast 是否复用封装？
- 模块边界上的类型是否明确？
- Windows 和 macOS 是否都能安装和运行？
- 微信开发者工具是否还能打开项目？

## 审阅归档

- 开发 Agent 完成小节点并需要交叉审阅时，必须先创建审阅请求包：
  `docs/reviews/requests/YYYY-MM-DD_<目标>_<期望审阅方>_review_request.md`。
- 审阅请求包要写清：背景、请先读、本轮已改、已验证、未验证项、重点审阅问题、
  期望输出路径。
- 所有审阅结果必须以文档形式落到 `docs/reviews/results/`。
- 聊天里的审阅输出只是临时载体；推进下一模块前，必须归档为
  `docs/reviews/results/YYYY-MM-DD_<目标>_<审阅方>_review.md`。
- 审阅归档文件需要保留原始审阅意见，并写清处置摘要。
- `docs/reviews/README.md` 必须追加对应请求和结果条目。
- 如果审阅方无法直接写文件，由当前执行 Agent 负责把审阅内容整理入档。
- 审阅 Agent 完成审阅归档后，负责提交一次 commit，作为该审阅节点的收口。
- 审阅节点 commit 不包含修 bug / 改实现；修订项进入下一轮开发任务或新的执行包条目。
- 如果审阅发现阻塞问题，commit 中记录阻塞结论和待修项，然后由开发 Agent 在下一轮处理。

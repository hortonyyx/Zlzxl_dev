# 模型分工

按照任务类型、审阅独立性和 token 成本来分配模型。

## 规划和需求

主力：

- GPT-5.5
- Opus

适合：

- 需求澄清。
- 产品取舍。
- 架构判断。
- 模块拆分。
- 实现前计划审阅。
- 困难 bug 诊断。

## 主要实现

主力：

- Codex
- Claude Code

适合：

- 功能实现。
- 边界清晰的重构。
- 测试补充。
- 和实现相关的文档更新。

## 交叉审阅

每个模块完成后：

- Claude/Opus 家族实现的内容，由 GPT-5.5/Codex 家族审阅。
- GPT-5.5/Codex 家族实现的内容，由 Claude/Opus 家族审阅。

审阅优先级：

1. bug 和回归风险。
2. 缺失边界场景。
3. 架构边界被破坏。
4. 缺少验证。
5. 过度设计或投机性代码。

## 里程碑审阅

大节点完成后，分别找下面两个模型独立审阅：

- GPT-5.5
- Opus

不要先把一个模型的审阅结果给另一个模型看。独立审阅更容易抓出不同问题。

## 备用和跑腿模型

备用实现：

- GLM 5.1

适合：

- 任务清晰且边界明确。
- 主力 token 不够。
- 输出可以快速检查。

跑腿、搜索、总结：

- Gemini Flash 3.1
- Haiku 类模型

适合：

- 搜索文件。
- 总结文档。
- 收集日志。
- 检查依赖和环境。
- 起草非权威笔记。
